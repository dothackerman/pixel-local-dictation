# Runtime investigation, 2026-10-12

Research and a bounded laptop smoke test, not a new engine decision or a phone benchmark. Requirements remain in [requirements](requirements.md); existing measurements and the closed experiment surface remain in [ADR-003–005](decisions.md) and [autoresearch](autoresearch.md). No phone access, model downloads, personal-audio inference, personal transcript copying, or production changes were performed for this note.

## Strongest finding: one Cohere instance already supports both languages

The current Kotlin `LanguageSwitchedRecognizer` eagerly builds one complete recognizer for German and another for English; Python `LanguageSwitched` does the same. They differ by language configuration, not weights. This is an application architecture choice, not a Cohere requirement. [Local Kotlin](../app/src/main/kotlin/ch/og/dictation/Engine.kt), [local Python](../tools/pipeline.py).

The **already pinned sherpa-onnx v1.13.8** supports per-stream language selection:

- Cohere's `DecodeStream` reads `s->GetOption("language")` before falling back to the model configuration, then builds the language tokens for that decode. It also accepts per-stream `use_itn` and `use_punct`. [Pinned implementation](https://github.com/k2-fsa/sherpa-onnx/blob/11afbd009a7f8c08f4bcf2fc1b265d0df4670fbf/sherpa-onnx/csrc/offline-recognizer-cohere-transcribe-impl.h).
- Kotlin exposes `OfflineStream.setOption(key, value)`; Python exposes `set_option`. The locally installed AAR contains both the Kotlin method name and the native `OfflineStream_setOption` symbol. This verifies API presence, **not successful inference**. [Kotlin API](https://github.com/k2-fsa/sherpa-onnx/blob/11afbd009a7f8c08f4bcf2fc1b265d0df4670fbf/sherpa-onnx/kotlin-api/OfflineStream.kt), [Python binding](https://github.com/k2-fsa/sherpa-onnx/blob/11afbd009a7f8c08f4bcf2fc1b265d0df4670fbf/sherpa-onnx/python/csrc/offline-stream.cc).

**Proposal:** retain the existing local language identifier and one Cohere recognizer; set `language` on every new stream before decoding. Keep language fixed within a take, reset it between takes, and preserve the current serial decode queue. No new weights or runtime upgrade should be necessary. Removing a duplicate model should materially reduce memory, but it does not imply exactly half the measured process peak: buffers, the identifier, session arenas, and temporary allocations remain. It does not inherently halve decode latency, since the existing code decodes only one selected instance.

**Executed laptop smoke test:** using installed sherpa-onnx 1.13.8 and the existing INT8 assets, constructed one recognizer with default language `en`, then set explicit per-stream languages `de/en/de/en`. Public guard clips were `de/7406_6765_000098.wav` (10.09 s) and `en/7021-85628-0005.wav` (5.01 s). All four outputs matched the saved two-instance Cohere guard outputs exactly after the existing Swiss-spelling normalization. Only parity booleans, timings and memory were emitted; no text was copied into this report. This validates actual Python inference and language alternation, not just API presence. The source comparison is `corpus/lab/runs/cohere-1f31656.json`'s public `guard` entries, not its personal takes.

The smoke process peaked at 3,465.4 MiB RSS, **without** a loaded language identifier. Load was 10.072 s; decode times were 6.017/2.376/4.165/1.800 s in that order. These are unisolated laptop observations during concurrent investigation, not comparable phone performance results. The memory result specifically prevents promising that one instance will necessarily meet the 3.5 GB phone criterion: it removes known duplication but leaves little apparent headroom, and platform-specific measurement remains necessary. No frozen pipeline/evaluator files or ledger rows were changed.

**Production-port trap:** Cohere's pinned model constructor explicitly rejects `AssetManager` loading. It loads encoder and decoder from filesystem paths. LabTest already uses private filesystem paths; the daily app's default asset path cannot be assumed to work. This calls for private local provisioning, not a storage permission or literal external SD card requirement. [Model implementation](https://github.com/k2-fsa/sherpa-onnx/blob/11afbd009a7f8c08f4bcf2fc1b265d0df4670fbf/sherpa-onnx/csrc/offline-cohere-transcribe-model.cc), [LabTest](../app/src/androidTest/kotlin/ch/og/dictation/LabTest.kt).

## Latency needs a separate experiment

The app queues closed chunks for serial offline decoding during recording; Stop flushes the remainder and waits for pending work. Therefore reducing duplicate model memory does not establish that Cohere meets the Stop budget. The final residual audio and any decode backlog determine waiting. [TakeTranscriber](../app/src/main/kotlin/ch/og/dictation/TakeTranscriber.kt).

**Proposed measurement:** log chunk emission time, queue start time, LID duration, inference duration, and Stop time separately. The current chunk timer excludes `beginTake`/LID, although paced Stop timing includes the end-to-end wait. Use that decomposition before optimizing the runtime. Range-find residual chunk duration versus accuracy using the existing policy; do not assume that shorter chunks preserve Cohere's observed accuracy advantage. If shorter chunks lose context, investigate overlapping windows or a short tail decoded at Stop as a new setup-round design, with explicit duplicate/omission checks. These are untested proposals outside the closed loop schema.

## Runtime paths and their actual relevance

| Path | What source evidence establishes | Priority / unresolved question |
|---|---|---|
| Single-instance Cohere on existing CPU runtime | Per-stream language is present in the pinned runtime and installed bindings. | First: removes a known duplicated allocation while keeping the model that earned a laptop accuracy gain. Must test alternating languages, output parity, peak memory and paced Stop delay. |
| Profile and tune ONNX Runtime for Cohere | sherpa configures session threads; XNNPACK is selected only if compiled in, otherwise falls back. Cohere has separate encoder/decoder sessions. | Second if latency remains unacceptable: profile whether encoder, autoregressive decoder, allocations, or queueing dominates. Provider availability is not evidence of actual accelerated operations or speed. |
| whisper.cpp CPU/Vulkan | Upstream supports Android, quantized Whisper and Vulkan. | Conditional challenger: useful only if a specific Whisper checkpoint/decoding path first demonstrates better accuracy. No evidence found of this Pixel/GrapheneOS combination meeting the budget. |
| Tensor G5 LiteRT | Official Google Tensor support exists; AOT compilation and vendor runtime are required. | Longer spike after a worthwhile model is established. Conversion, operator coverage, numerical parity and actual GrapheneOS execution remain unverified. |

Sources: [pinned sherpa session construction](https://github.com/k2-fsa/sherpa-onnx/blob/11afbd009a7f8c08f4bcf2fc1b265d0df4670fbf/sherpa-onnx/csrc/session.cc), [whisper.cpp inspected commit](https://github.com/ggml-org/whisper.cpp/blob/0c7be696371069e0baa2515ed7aa08d5a5473aa6/README.md), [LiteRT NPU guide](https://developers.google.com/edge/litert/next/npu).

ONNX Runtime does not list a ready Google Tensor provider or native Vulkan provider in its current provider catalog. The existing Cohere CUDA I/O binding path is NVIDIA-specific. QNN is Qualcomm-specific. Direct ONNX Runtime integration would expose lower-level control, but would not by itself produce a Tensor backend or better recognition. Shared ORT session allocators can reduce memory in some cases, but eliminating the duplicated recognizer is a simpler first hypothesis than introducing allocator management. [Provider catalog](https://onnxruntime.ai/docs/execution-providers/), [memory guidance](https://onnxruntime.ai/docs/performance/tune-performance/memory.html), [Cohere implementation](https://github.com/k2-fsa/sherpa-onnx/blob/11afbd009a7f8c08f4bcf2fc1b265d0df4670fbf/sherpa-onnx/csrc/offline-cohere-transcribe-model.cc).

For Whisper, a runtime comparison should hold weights, language policy, task, chunk boundaries and decoding settings constant first. Changing all of these alongside Vulkan makes any accuracy gain uninterpretable. A large-v3 challenger and the already tested turbo export are separate model hypotheses. Vulkan support is a buildable upstream path, not a transferable Pixel speed claim; inspect backend selection and compare CPU versus GPU on the actual device under the existing phone rules. [whisper.cpp build and supported models](https://github.com/ggml-org/whisper.cpp/blob/0c7be696371069e0baa2515ed7aa08d5a5473aa6/README.md).

Google's current Tensor documentation lists G5 and states the cloud-project prerequisite does not apply to Pixel 10. The NPU guide says Google Tensor supports AOT but not on-device JIT compilation. It also documents partial delegation/fallback and, from LiteRT 2.3.0, a Google Tensor runtime Maven package. Thus old blanket claims that Tensor acceleration is inaccessible should not become a design constraint. None of this demonstrates support for these ASR exports on GrapheneOS. Start with a locally bundled official sample, then one fixed-shape encoder subgraph; verify accelerator execution and reference numerical outputs before attempting the dynamic decoder. No cloud inference or security changes are needed as part of this proposed investigation. [Tensor setup](https://developers.google.com/edge/litert/next/tensor-sdk), [NPU deployment and fallback](https://developers.google.com/edge/litert/next/npu), [Tensor compilation FAQ](https://developers.google.com/edge/tensor-sdk/tensor-faqs).

## Smallest decisive next tests

1. In a setup round, make one-instance Cohere a separate implementation experiment. Match old two-instance outputs on identical existing clips, alternate German/English repeatedly, include short ambiguous starts and cancellation, and assert the language option on every stream. Keep the evaluator unchanged.
2. Re-run memory and paced latency on the permitted benchmark path. Record cold load, peak RSS/PSS, queue wait, LID time and decode time separately. A memory pass and a latency pass are independent outcomes.
3. Only if latency fails, profile Cohere before choosing shorter residual chunks, CPU tuning or an accelerator. Preserve the already measured accuracy while testing one speed intervention at a time.
4. Maintain an independent model-quality track. Runtime work is justified by enabling an accuracy winner to fit the product budget; it cannot make the current Parakeet weights know missing names by itself.
