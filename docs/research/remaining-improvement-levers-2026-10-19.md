# Where remaining improvement is likely to come from

19 October 2026. Analysis only: existing raw results, source and current upstream documentation; no inference, downloads or device access. [Requirements](../requirements.md) still require automatic local English/German recognition, improved speed **and** accuracy against installed FUTO, and preserved meaning.

**Judgment:** the strongest demonstrated opportunity is making useful vocabulary biasing affordable. The current CPU implementation already shows a quality gain on supplied vocabulary, with a substantial execution cost. This supports focused precision/runtime work; it does not establish that another general app rewrite, bigger model or Pixel accelerator is the answer. A cheap new-model quality screen remains the best independent challenger. Daily correction benefit and generalization are still unresolved.

## What the evidence actually locates

I rescored raw phone takes with [the existing evaluator](../../tools/evaluate.py): baseline German/English errors **46/22**, FP32 beam-8 dictionary **35/11**, Cohere **24/23**, over 584/632 words. These agree with the [completed allocation results](../archive/allocation-2026-10-19.md#quality); that archive owns the full resource/quality tables and limitations. Raw sources: [baseline](../../corpus/lab/allocation-v1/runs/s3-phone-01-baseline-stock.raw.json), [FP32 dictionary](../../corpus/lab/allocation-v1/runs/s2-phone-07-dict-beam8-fp32-s20-stock.raw.json), [Cohere](../../corpus/lab/allocation-v1/runs/s3-phone-07-cohere-stock.raw.json).

The useful mechanism is narrower than “FP32 improves accuracy.” Earlier matched laptop primary-feed results are FP32 greedy **45/24**, FP32 beam-8 without dictionary **42/26**, dictionary twin **35/11**. Precision/search alone did not produce an English gain. All 43 supplied dictionary entries also occur in the scripts' term files. That is contextual recognition of known vocabulary, not unseen-name evidence. Ten takes contain eight unique scripts; extra feed schedules/repetitions add no new content. [Raw greedy](../../corpus/lab/runs/fp32-fec1163.json), [beam](../../corpus/lab/runs/beam8-fp32-gate-2d11d13.json), [dictionary twin](../../corpus/lab/runs/dict-beam8-fp32-s20-2d11d13.json), [dictionary](../../corpus/lab/dictionary.txt), [take mapping](../../corpus/takes.json).

Raw endpoint counters locate real inference cost. In the second stock FP32 process, a German Stop just after a chunk boundary waits 7.944 s while a 20.59 s chunk takes 8.038 s to decode. Even an early Stop with no active/queued work waits 4.374 s for a 10.09 s chunk. Therefore scheduling can reduce exposed work at boundaries, but cannot remove the cost of decoding an initial short take. [Raw endpoint counters](../../corpus/lab/allocation-v1/runs/s2-phone-07-dict-beam8-fp32-s20-stock.raw.json).

[TakeTranscriber](../../app/src/main/kotlin/ch/og/dictation/TakeTranscriber.kt) serially decodes closed independent chunks, then flushes the remainder at Stop. It exposes no incremental encoder cache. [MeasurementRun](../../app/src/androidTest/kotlin/ch/og/dictation/MeasurementRun.kt) times the complete recognizer call; `queueWaitMs` includes the final completion task, so adding that wait to decode time double-counts work. Smaller tails/earlier commits could help, but shorter context already has a quality tradeoff; repeated overlapping offline windows add computation.

All latest measurement variants have profiling disabled. An existing [public laptop smoke trace summary](../../corpus/lab/pre-smoke-refresh-20261014/release-1a/profile-summary.json), checked against its [raw trace events](../../corpus/lab/release-1a/smoke-profile.profiles/), records encoder/decoder/joiner model-run totals of 1.351/1.266/1.151 s, all CPU. Native search is unmeasured. This does **not** locate the phone bottleneck, but already contradicts assuming the encoder is necessarily the whole cost.

## Ranked levers

| Priority | Lever and plausible benefit | Evidence / what would reject it |
|---|---|---|
| 1 | Preserve the dictionary candidate's quality at lower cost: selective precision, then a supported execution alternative; scheduling complements either. | Highest evidence of an existing useful mechanism. Current [quantizer](../../tools/quant_variant.py) only selects operator types; ORT also supports per-channel weights and exclusions. Reject a cheaper export if matched beam/dictionary output loses the gain or collapses on guards. Another broad beam/chunk sweep has weaker justification after existing tuning. [ORT guidance](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html). |
| 2 | Screen a cheaper model before expensive integration. Whistle is the simpler automatic-language challenger; Moonshine offers actual streaming but requires automatic routing. | No personal quality evidence for either. Whistle's publisher offers German/English, keyword biasing and Android artifacts, but headline speed is Apple M4 Pro. Moonshine lists German Small and English Medium Streaming; separate-language quality cannot establish a router's quality. Reject before Android work if neither unbiased nor dictionary-twin quality earns it. [Whistle](https://www.cactuscompute.com/blog/whistle), [Moonshine models](https://moonshine-voice.readthedocs.io/en/latest/models/available-models/), [existing bounded proposals](model-options-2026-10-14.md). |
| 3 | Pixel Tensor/GPU acceleration, conditional on a valuable quality candidate and attributable compute cost. | Current [provider](../../app/src/main/kotlin/ch/og/dictation/RuntimeConfig.kt) explicitly selects CPU. Google documents Tensor G5 support and AOT LiteRT execution; this is a real feasibility path. No GrapheneOS sample execution, ASR conversion, operator coverage, numerical parity or useful complete-path speedup is established. LiteRT permits partial delegation/fallback: successful invocation alone proves little. [Tensor SDK](https://developers.google.com/edge/litert/next/tensor-sdk), [deployment/fallback](https://developers.google.com/edge/litert/next/npu). |
| 4 | Larger checkpoint for residual general recognition errors. | Potential new quality ceiling, highest resource uncertainty. Cohere already shows German benefit without an English win here. Qwen publishes larger multilingual checkpoints, but publisher averages cannot establish personal benefit. Reference-quality evidence must precede conversion/phone work. [Qwen source](https://github.com/QwenLM/Qwen3-ASR), [reference-screen proposal](model-options-2026-10-14.md#2-qwen3-asr-17b-with-a-reference-to-runtime-parity-check). |

Accelerators buy execution headroom; they do not create recognition accuracy. Nor is the app baseline's subsecond wait an approved universal requirement: the observed slower candidates may still beat FUTO. The actual product decision must include correction effort and complete automatic phone behavior; existing FUTO observations use different spoken takes. [Historical comparison](../evaluation/results.md#run-of-2026-10-10).

## Smallest next decision

**Seek the cheapest way to retain the demonstrated vocabulary benefit; do not launch another allocation campaign.** First use existing per-take errors and endpoint counters to state which residual cost the next change targets. Existing evidence cannot choose encoder precision versus decoder/search runtime: the missing datum is their phone time split, not another same-build memory delta. A bounded profile is justified only if that split changes the chosen engineering action; no profile run is commissioned here.

If a cheap Whistle quality screen can precede substantial backend engineering, prefer that screening order: it could remove the need for a costly conversion project. This is a proposal for later inference, not evidence that Whistle wins. If it fails, the existing biasing candidate remains the stronger lead. Keep Moonshine routing and larger checkpoints behind demonstrated reference quality.

Before claiming daily improvement, freeze vocabulary/settings and validate short spontaneous speech, unfamiliar names, wrong-language choices and correction/meaning cost against installed FUTO, separately per language. A known-script win may justify that validation; it cannot replace it. No new recordings are requested here. Same-build memory confirmation is useful only if either possible result changes a deployment decision; current evidence does not make it a prerequisite to these choices.
