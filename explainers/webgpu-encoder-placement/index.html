Issue #4 · ADR-022 · Pixel 10 Pro XL

Why WebGPU refused the encoder

On 21 October we tried to run the speech encoder on the phone's GPU. The test stopped before the first calculation. This page explains why, starting from zero. Each level uses only words from the levels before it.

1Level 1 · Start here

What happens when you dictate

You press the microphone key in FUTO and speak. One recording, from panel open to Stop, is a take. The app turns the take into text in four stages:

Earlier measurements (ADR-015) showed that the encoder does most of the work. The phone has two chips that can do this work:

CPU

The main processor

A few very fast, flexible calculators. They work one after another. Good at small jobs where each answer depends on the one before.

GPU

The graphics chip

Thousands of small calculators. They all do the same simple sum at the same time. Great for millions of identical multiplications. Bad at three numbers that depend on each other.

The encoder is mostly millions of identical multiplications. So the plan was: keep everything else the same, and move only the encoder to the GPU.

Takeaway: we tried to move one stage, the encoder, from the CPU to the GPU.
2Level 2

A model file is a recipe of small steps

The encoder is stored as an ONNX file (encoder.onnx). ONNX is a common file format for AI models. Think of it as a recipe:

Steps (nodes)

Each step is one simple operation: add, multiply, reshape, compare. Steps connect in a network called a graph. Our encoder graph has 4,955 steps. ORT cleans it up before running (merges and removes some steps). On the PC, about 2,273 steps remained.

Ingredients (weights)

The learned numbers that make the model "know" speech: 2.4 GB in encoder.weights. These never change.

Op type

The kind of step, e.g. MatMul (big multiplication), Conv, Gather (pick one item from a list), Shape (ask "how big is this?").

Written as simple pseudo code, the whole encoder recipe looks like this:

pseudo code · what the encoder graph computes
def encoder(audio_features, length):
    # frame: 10 ms of audio, described by 128 numbers
    # audio_features: float numbers, shape [1, 128, frames]
    # length:         one whole number = how many frames are real

    x          = subsample(audio_features)       # keep 1 frame of 8 (rounded up)
    new_length = shrink_length(length)          # 17 -> 3 in our test
    mask       = make_padding_mask(new_length, x) # which frames are real?

    for layer in range(24):
        x = conformer_layer(x, mask)           # the heavy sound math

    return x, new_length                      # shape [1, 1024, 3] and the number 3

Teal lines are the tensor math. Amber lines are small shape work. Keep these two colors in mind: they are the whole story.

Takeaway: the encoder is thousands of small steps. Most do tensor math. Some only count and measure.
3Level 3

Who executes the recipe: ONNX Runtime and its workers

ONNX Runtime (ORT) is the program that reads the recipe and runs it. ORT does not do the math itself. It hands each step to a worker. ORT calls a worker an execution provider (EP). Each worker owns one kind of chip.

"WebGPU" is a standard way to talk to GPUs, first made for web browsers. ORT uses it because it works on many GPUs, including the one in the Pixel. Vulkan is the phone's own low-level GPU language. The driver is the software that speaks Vulkan to the chip. Dawn translates WebGPU into Vulkan.

A worker can only do a step if it has a kernel for it. A kernel is a ready-made program for one op type and one number type, for example "MatMul with float numbers on the GPU". No kernel means the worker cannot do that step.

Takeaway: ORT is the manager. The CPU and the GPU are two workers. A worker needs a kernel (a skill) for each step.
4Level 4

Three kinds of values in the recipe

float32

Measurement numbers

Numbers with decimals, like 0.0371. All sound features, weights and intermediate results. Millions per take. GPUs are built for these.

int64

Counting numbers

Whole numbers, like 17 or 3. Lengths, sizes, positions. Only a handful per step. The GPU worker can do only some of these steps.

bool

Yes/no values

True/False. Used for masks: lists that say which frames are real speech and which are padding.

The 32 and 64 are the number of bits (memory cells) used to store one value.

Why does a speech model need counting at all?

The encoder accepts audio of any length. So it must measure every size while it runs. It was also built to process several recordings at once, side by side. A short recording is then filled up with empty frames: padding. The model must know which frames are real, or the padding pollutes the result. Our app sends one take at a time, so the mask is usually all "yes". But the recipe still contains every counting step:

pseudo code · the shape work (amber)
# example with 5 frames, 3 of them real
def make_padding_mask(real_length, x):
    total   = shape(x)[2]              # "how many frames is x?"   -> 5
    pos     = range(total)             # [0, 1, 2, 3, 4]           int64
    return pos < real_length            # [T, T, T, F, F]           bool

# later, inside each of the 24 layers (tensor math, teal):
scores = where(mask, scores, -infinity)    # ignore the padding frames

Shape-work steps like these repeat in all 24 layers, mostly to measure sizes before the data is reshaped. Together they become hundreds of tiny steps: Shape, Gather, Unsqueeze, Concat, Reshape, Less, Not…

Our test input: 17 feature frames (0.17 s of silence) became 3 encoder frames. That matches the CPU output shape [1, 1024, 3].

Takeaway: besides the tensor math, the encoder contains hundreds of tiny shape-work steps on whole numbers and yes/no values.
5Level 5

Before running, ORT assigns every step to a worker

When the app creates a runtime session (loads the model and prepares it), ORT goes through all steps and decides which worker does each one. No audio is processed yet. The runtime session is created once, and every later take reuses it. So a failure here means no take can ever run.

One more fact first. The CPU and the GPU have separate memory. Every hand-over copies data from one memory to the other and waits for the other chip. One hand-over costs more time than adding three numbers. A hand-over there and back is a round trip.

ORT asks two questions for each step:

pseudo code · simplified from ORT 1.31 source
def assign_workers(graph):
    for step in graph.steps:
        if not gpu.has_kernel(step.op_type, step.number_type):
            step.worker = CPU      # Question 1: can the GPU do it at all?
        else:
            step.worker = GPU

    # Question 2: is the CPU simply faster for this step?
    # This check ALWAYS runs. There is no setting to switch it off.
    for step in cpu_is_faster(graph):
        step.worker = CPU

Takeaway: ORT always sends some shape-work steps to the CPU, for two reasons: the GPU can't do them, or the CPU is faster for them. This is normal and on purpose.
6Level 6

Our strict rule: "zero steps on the CPU, or stop"

In ADR-020 we decided the GPU test must be honest. If ORT secretly ran part of the encoder on the CPU, a GPU speed result could be misleading. So we switched on one ORT setting:

pseudo code · what the setting does
session_options["session.disable_cpu_ep_fallback"] = "1"
gpu_options["enableInt64"] = "1"   # also on: adds SOME int64 GPU kernels, not all

# ... ORT runs assign_workers(graph) from Level 5, then:

if any(step.worker == CPU for step in graph.steps):
    raise Fail("graph nodes ... assigned to the default CPU EP,
               but fallback to CPU EP has been explicitly disabled")

run(graph)   # never reached in our test

We had the int64 switch on. It shrinks the Question 1 group, but it does not touch Question 2. The rule has no exceptions and no list of allowed steps. One CPU step is enough to stop. The real ORT code is in inference_session.cc:3177-3182.

Takeaway: we told ORT to stop if even one step lands on the CPU.
7Level 7 · The answer

The collision: Level 5 meets Level 6

Put the two levels together. ORT always sends some shape-work steps to the CPU (Level 5). Our rule stops at the first CPU step (Level 6). So the runtime session stopped during preparation, before any calculation. The GPU never received a single number.

To see exactly which steps went to the CPU, we repeated the test on the PC with the official ORT WebGPU package and the same settings. The PC showed the same error. Then we ran it once without the strict rule and asked ORT to list where every step went:

Root cause

The GPU did not fail. Our strict rule and ORT's normal behavior do not fit together.

ORT always keeps some shape-work steps on the CPU. Some have no GPU kernel. ORT moves the others on purpose, because the CPU is faster for them. Our rule allows zero CPU steps. With the unchanged encoder and the standard ORT, the two can never agree. So the session stops every time.

on purpose

ORT's own log text says it "explicitly assigns shape related ops to CPU to improve perf".

cheap

Each counting step touches only a few numbers. Moving them to the GPU would add slow round trips.

no switch

ORT 1.31 has no option to turn off Question 2 and no allow-list for the strict rule.

Next steps · your decision

Three ways forward

To continue, one of three things must change: the rule, the model, or the runtime.

recommended

A · Change the rule

Allow shape-work steps on the CPU and check the placement ourselves. Read ORT's list of which worker got each step. Pass only if every CPU step is int64/yes-no shape work and every tensor-math step is on the GPU. This keeps the honest-test intent with the unchanged model and standard ORT. It needs you to update ADR-020.

change the model

B · Remove the counting

Create a new encoder file for one fixed audio length, so all sizes become constants and the shape-work steps disappear. Or compute the mask in the app and give it to the model. This could reach zero CPU steps, but it changes the length handling that ADR-020 wanted to keep.

change the runtime

C · Build our own ORT

Remove the "CPU faster" check and write the missing GPU kernels. We would have to maintain our own copy of ORT. The result is probably slower, because it forces the round trips ORT avoids on purpose.
